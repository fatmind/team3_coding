## 1. 问题

北极星（分区块验证）：mock 只属"造数据"区块；一旦生成，就当真实数据往下走证据卡/机会卡。两次最严重翻车（校验器 7 轮不通过、机会卡跑出全是低优先级 等）都违背了它。

## 2. 根因

**读复盘 + 认错 ≠ 行为改变。** Agent 写什么，是被它眼前的上下文带着走的，认错只发生在嘴上。分三层：

### 上下文内容

1. **过期文档还在原地，一句"禁止参考"没用。** app_design §5 把过期文档标为"保留但禁止参考"，但文件全在 `spec/` 里，照样被读进上下文。满目录都是"哈希链/反查/冻结"这些字眼，Agent 写着写着就跟过去了——#297 无中生有写出"哈希链仍不在管线"就是直接证据。
2. **同一个 session 背着全部旧历史。** 这个 arch 亲手搭了哈希链、验收了 M5 F1、带队修过"hash 链 bug"，几百轮旧对话的分量远大于新读的两份文档。所以"#293 真诚认错 → #296 又复发"。

### Agent 行为

3. **信号弱**：方向/细节/实现/代码混杂，一次多问，人类挑不出要拍板的关键。
4. **不敢掉头**：越修越多时只在现状上补救，识别不出"方向错了"。
5. **套模板 + 迎合**：拿通用做法填空（如训练/测试切分），不从"当前阶段要什么"出发想，被追问时硬凑分类显得完整，而不是说"这不重要"。

## 3. 改进项

先立一条总原则，再按 4 条往下组织。

> **总原则：别指望 Agent 记住规则。** prompt 已经 16000 字，规则写得越多、每条越记不住；"靠 prompt 写 NEVER 管不住 Agent"这条教训 loop_001（2026-06）就总结过，7 月照样犯——连教训本身都没能靠写下来生效。规则要做到**不靠记性也起作用**，主要优化：
> 0. **过期及时清理**——避免污染
> 1. **做成格式**——想违反都违反不了（如回复人类消息固定格式）；
> 2. **交付前自查清单**（暂缓，见 §2）——交付前，再用清单再查一遍，防止做的时候万一没遵循，发现问题继续改（注：反向要求你得要有明确的评测标准）；
> 3. **减少 system prompt 负担**——部分拆为 reference；

每条写「怎么做 + 怎么验收」。**lazada-hackathon5 是验收项目**：每条改完，都回这个项目上实测。

### 0. 过期及时清理——避免污染

**怎么做（一）：方向推翻 = 一条 `rebase` 消息，daemon 特殊功能保证顺序**

- 人类发 `rebase` action（web 按特殊格式匹配 [rebase:xxx]，本质是写一条消息进 actions.jsonl，方向推翻这件事自动留痕；rebase 是人和 daemon 的对话，to 固定 `T3`——chat 界面 daemon 就显示为 T3）：

  ```jsonl
  {"action":"rebase","from":"human","to":"T3","message":"方向已调整，以新基准为准 [reread: spec/app_design.md, ...]"}
  ```

- daemon 收到后按序执行（顺序由 daemon 保证，不靠人记）：
  1. 独立开一个归档 Agent（code-cli 全新 session）全局扫描 spec/ 出归档提案（含 feature_list.json / progress.txt 等派生文件；actions.jsonl、rebase_log.md 是系统文件绝不可动，decisions.md / experience.md 只可局部清理废止条目、不可整文件归档），人类回 `[rebase: 确认]` 才执行、可直接说调整意见或 `[rebase: 取消]`；
  2. 归档完成后追加 `spec/rebase_log.md`，把 `.team3-project.json` 里 arch session 置空（rebase 只对 arch 有意义——只有它长 session 背历史，dev/uat 每任务天然新 session）；
  3. daemon 以 `T3` 身份写一条重启消息派给 arch：归档已完成 + 按「全局要求」重建项目全局认识、以当前 spec/ 为唯一基准。rebase 原文不重放——归档 Agent 已执行过它。

**怎么做（二）：decision_log.md 拆成两个文件，各自格式重立**

现在的写法不行：483 行"背景/结论"长叙事，一条里混着三种东西——给下个 feature 的交接约束、可泛化的教训、取证细节，真正有用的信号被埋在里面，人和 extract.mjs 都没法用。

- **`spec/decisions.md`——只放生效的人类决策**，一条一行：

  ```
  日期 | 一句话决策（大白话，≤100 字）
  - <想象你在给别人讲述你的决策逻辑，逻辑自洽> 
  - <多条分开>
  ```

  生效条目 ≤20 条，再多说明记的是流水账，相似内容优先合并。

- **Agent 经验教训拆到 `spec/experience.md`**，三角色直接按格式追加（写入不走工具），每条：

  ```
  ## 日期 | 角色 | 一句话概述
  - 问题
  - 原因
  - 应该咋做
  - ref
  ```

- **经验怎么记（三条规矩）**：
  1. **入库先分拣**：把项目名、文件名、字段名扒掉后结论仍成立的，才算经验。
  2. **条目两层**：一句话头部（什么时候用 + 能照做的结论），正文只有固定字段 —— 问题 / 原因 / 应该咋做 / ref，禁止自由散文。
  3. **两层各有读者**：Agent 用只读 cli 省上下文（`experience.mjs list` 查头部索引、`show <序号>` 查单条详情）；self_improvement 分析读全文件，确保信息不丢失。写入门槛和"格式坏了的代价"成正比——经验库是给人和 LLM 读的文本，直接写 md 就够，不像 actions.jsonl 必须 cli 把关。

- **loop 能力同步**（extract.mjs / app_self_improvement.md 已改）：issues ← experience.md（行号增量，和旧 decision_log 同机制）；habits ← decisions.md（≤20 条生效快照，不做增量、全量带给 LLM 判断）；旧项目只有 decision_log.md 的走原逻辑，不迁移。

### 1. Agent 需要人类决策的 —— 格式和自查【已完成】

**怎么做（一）：固定格式**

to_human 三类消息各有固定开头，不得混用：要人决策 `【要你拍板】`、要人给输入 `【要你补充】`、纯通知 `【报备】`。决策消息固定三块：

```
**要你拍板** 
<大白话一句，带上"不这么做会怎样">
**思考逻辑**
1~3 条，每条一行
**自查约束**
①、⑦ 过
```

- 不给选项让人选——分析选项是 Agent 的活，只给一个最优建议；人类要么回「同意」，要么大白话反驳
- 可逆的小事不进决策消息：直接干，之后在交付消息里报备一句

**怎么做（二）：发出前自查七条**（按目的设计，目的互不重叠，每条可判 yes/no）

发不发：

| # | 目的（防什么病） | 自查动作 |
|---|---|---|
| ① | 防止无效提问 —— 不值得人决策的，拿去问，消耗人类决策力（41 次问询主因） | 假设不问、直接干了，事后人类发现——会要求返工/发火吗？不会 → 不发，干完在交付消息里报备 |

敢质疑：

| ② | 防在错误基础上打补丁 —— 不敢质疑"方向对不对"，只想着去"怎么打补丁" | 两问：你的前提人类否定过？同一问题在多次修复？命中任一 → 要拍的板换成"方向还继不继续"，摆疑点，不是请批第 N 个补丁 |

问什么：

| # | 目的 | 自查动作 |
|---|---|---|
| ③ | 防一次问多个 —— 决策点多了，人类挑不出关键 | 当出现多个决策点，这种复杂情况，你先回到整体视角考虑、先从整体问题，再一层层往下拆问题，坚决不能一次平铺很多问题 |
| ④ | 防没独立思考 —— 把没做完的分析递给人类，让人替 Agent 思考 | 出现 "或者 / 都可以 / 看你 / 你觉得…" 任一 → 分析没做完，做完再发 |
| ⑤ | 防套模板/硬凑/旧方向惯性 —— 理由从通用做法或旧记忆搬来，不是从当前阶段推出 | 每条思考逻辑接"因为当前阶段要X"：接不上 → 删；删完建议站不住 → 建议本身是拼凑的，整条重想 |

怎么说：

| # | 目的 | 自查动作 |
|---|---|---|
| ⑥ | 防黑话/防大话/防排比 —— 人类读不懂自己在拍什么板 | 新人测试：读给一个新人，他能理解复述出 "要决定什么、不这么做会怎样"吗？ |
| ⑦ | 防细节稀释信号 —— 方向和细节/实现混杂，重要的被淹没 | 逐句问 "删掉这句，人类会拍错板吗？"不会 → 删；文件名、函数名、字段名、代码、表格、commit log 等默认全是细节 |


**怎么做（三）：write-action.mjs 拦截 + 干净 LLM 判卷**

拦截点不在 daemon——daemon 靠 watch actions.jsonl，看到消息时已经写进去了，"写入前拦截"在当前架构做不到。而 write-action.mjs 是 Agent 写 actions.jsonl 的唯一入口，且是 Agent session 内的一次工具调用：**校验不过 → exit 1 + stderr 输出哪几条没过 → Agent 同一轮看到失败原因、自己改写重发**，"自我检查一次"零额外机制自动闭环。

- **拦截范围**：仅 `to_human` 消息开启检查，agent 间消息（dev_do/uat_check 等）不拦——量大、延迟敏感，且不是本次要治的病（治的是消耗人类决策力）。
- **判卷者必须是新开的干净上下文**：
  - 判卷：code-cli llm，输入只有"这条消息 + 七条自查清单"，输出 JSON：每条 yes/no + 一行理由；
  - 改卷：原 Agent 自己改 —— 它有任务上下文，判卷者没有也不需要。
- **检查直接就 LLM**，不做脚本层前置检查。
- 代价：每条 to_human 消息多一次模型调用，几秒延迟 —— to_human 本来低频，可接受；Agent 可能学会改措辞骗过判卷 —— 接受，人类最终能看到消息，判卷只提高底线不保真。

验收（lazada-hackathon5 实测）：
- [x] 判卷机制上线：write-action 对 to_human 判卷，不过 exit 1 + stderr 列未过项（daemon 测试套件含判卷用例，372 pass）
- [ ] 拒绝用例：把 #284、#290、#296 三条原始消息做成判卷的固定测试用例——判卷必须能拒掉它们（分别命中⑤套模板、④硬凑、违禁词"哈希链/冻结"）；再配一条合格消息可通过
- [ ] 通过真实需求开发验证

### 2. 交付前自查清单——防止做的时候没遵循

**结论：暂缓，不单独建清单/加交付关。** 理由：

- 第 0 条做完后，"人类否定过的概念"的唯一权威源头就是 `spec/decisions.md`——旧文档归档 + 置空 session 已切断输入污染，不需要再维护第二份清单文件。
- arch system prompt 的「全局要求（每个 MODE 都遵守）」本就要求开工先读 `spec/app_design.md` 和 `spec/decisions.md`，交付前再加一道检查属于重复投入，只增大 token 消耗，意义很小。

观察与重启条件：

- 0/1 落地后在本项目跑真实需求，盯一个指标——"人类否定过的概念再次出现在成稿"的次数。#296 那版 §2.3 成稿留作观察用样本（含"哈希链/冻结"两处）。
- 若复发（说明模型通用先验绕过了开工阅读），再回来做交付关：复用第 1 条的 write-action 判卷机制扩到交付消息，卷子 = decisions.md + 溯源题。不新建清单文件，不往 prompt 堆规则。

### 3. 减少 system prompt 负担——部分拆为 reference【已完成】

背景：prompt 整串走 `--system-prompt`，16000 是 CLI 硬上限；改前 arch 有效长度 16152 已超线（dev 15241 / uat 14593）。

**做法：按风险从低到高三步走**，每步都问同一句"这段离开常驻上下文，行为会变差吗？"——答不了的不动：

1. **重组**——每个角色只背自己需要的。team3.md 整份内联进三份 prompt，只有一个角色用的内容挪去那个角色：feature_list / modules_progress 的 schema、progress.txt 模板 → arch；uat 本来就被禁读这些文件，卸掉反而更黑盒
2. **去重**——判含义不判字面。两处说同一件事、照任一处执行行为都一样才算重复；协议的发送方/接收方两端、格式定义 vs 步骤内提醒、红线的刻意复述都不是重复，不动
3. **外置**——三问过滤，过不了就留在 prompt：值得拆吗（长、细节多、特定场景才触发）？拆得开吗（内容独立不与主流程交织）？拆后读取条件够明确吗（入口二元：消息带标记/文件存在，零犹豫）？立场：Agent 是执行者本来就想遵循指令，外置不是防它不读，是防长细节稀释主流程信号

**实现结果**：

- 6 个 ref 文件（源码在 `human_coding/`，打包进 `pkg/assets/ref`）：tech-stack、dev-html-prototype（并入原 html-prototype-trans-template）、dev-ui、dev-init-sh、arch-ui、uat-scaffold；不再下发到业务项目根，init-workspace 的下发逻辑已删
- prompt 入口统一格式、嵌在触发步骤里：`> <触发条件> → 先 Read {ref}/xxx.md（一句话说明）`
- `{ref}` 占位符与 `{cwd}` 同点展开（code-cli buildArgs + ref-dir.js：打包模式指 `$TEAM3_PKG_DIR/assets/ref`，源码模式指 `human_coding/`）；embed-prompts 给 `{ref}` 留了和 `{cwd}` 一样的展开预留
- 长度：arch 16152 → 13943，dev 15241 → 11011，uat 14593 → 11839，全部低于 14500 目标线
- 顺带修掉一批不一致：`note` 补进 action 枚举、uat 的 to_human 示例补三类开头、uat-evidence 模板 JSON 尾逗号（照抄必挂校验）、dev 全局认识并入头部「全局要求」后 STEP 重编号、Playwright 统一为 puppeteer-core 等

**新规则的去处**（大原则，无机制保障，靠人把关）：人类决策 → `spec/decisions.md`；工具用法/格式/案例 → `{ref}/`；只有"身份、流程骨架、红线"级别才进 prompt。

验收：
- [x] 三角色 effective ≤ 14500（`node build/embed-prompts.js` 实测）
