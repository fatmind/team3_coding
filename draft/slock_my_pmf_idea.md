## 二、运转流程图（标注人类投入的轻重）

```
======== 人类重度投入阶段 ========

人类有一个产品想法
    |
    v
人类 + Arch 讨论，补全产品整体设计（app 级）
    |  人类说：这是我的初步想想 xx.md，你独立思考、批判，我们讨论下
    |  Arch 问：那 xx 场景流程是？实体间关系是？
    |  来回几轮，产出：app_spec.md
    |
    v
人类 + Arch 讨论，拆模块、定模块 spec（module 级）
    |  Arch 提议：拆成 3 个模块，各自负责 xxx
    |  人类确认/调整模块边界
    |  每个模块产出：module_spec.md
    |  用户使用场景要尽量列全（这是后续 UAT 展开验证的锚点）
    |  比如 "有x种使用场景，场景 1 使用动线、每步验证"，场景不能漏
    |  从 app 整体设计，到 module 拆解和细化
    |
    v
人类确认："可以开始了"
  （从此刻起，人类不再主动推进，只在被上报时介入）

Arch 读 app spec + module spec + 项目规范 + 长期规范
    |
    v
Arch 把 module 拆成 feature list（按 init_feature.md 格式）
    |  checkpoint 要尽量详细（见下方「feature checkpoint 要求」）
    |  但本质仍是 AI 自己定义的验收标准
    |
    v
Arch 分配 feature 给 Dev
    |  附带完整上下文：app spec + module spec + feature + checkpoint
    |
    v
Dev 实现 + 按 checkpoint 自测
    |
    +---> checkpoint 通过 -> 提 PR -> CI 跑回归
    |                                    |
    |                              +-----+-----+
    |                              |  绿        |  红
    |                              v            v
    |                           merge        Dev 修复 -> 重跑
    |
    +---> checkpoint 不通过 -> Dev 修复
    |                              |
    |                         尝试很多次、还是不行
    |                              v
    |                    标记 blocked，上报 Arch
    |
    v
该 module 所有 feature 完成
    |
    v
======== UAT 整体功能验收阶段 ========

UAT 独立登场（不看 Dev 实现、不看 Arch 的 feature 拆分）
    |
    |  UAT 只读：app_spec.md + module_spec.md
    |  （视角隔离：从产品整体和模块定义出发，不受实现细节影响）
    |
    v
UAT 从 app spec + module spec 出发，设计完整验证集
    |  站在用户角度，把 spec 里的每个场景展开成具体验证步骤
    |  比如 spec 说"支持分页加载"，UAT 展开为：
    |    - 滚动到底部触发加载
    |    - 加载中显示 loading 状态
    |    - 加载后内容拼接正确，无重复
    |    - 空数据时显示"没有更多"
    |    - 网络异常时显示错误提示
    |

    |

    |                              Arch 判断：
    |                              是 bug -> 分配给 Dev 修
    |                              是 spec 歧义 -> 上报人类

人类收到：UAT 报告 + 可体验的地址/截图
    |
    +---> 确认 OK -> 进入下一个 module
    +---> 不 OK -> 给反馈（新 feature 或修改现有 feature）-> Arch 调整
    +---> 前端 UI 需要调整 -> 直接给 Dev 反馈样式/交互问题（todo 待讨论）

======== Arch 上报触发点（3 种情况）========

触发 1：一个 module 通过 UAT 验证
    -> Arch 上报人类：module X UAT 通过，请最终验收
    -> 附上 UAT 报告 + 体验地址

触发 2：Arch 发现需求前后有冲突
    -> 比如实现中发现 module A 和 module B 的接口设计矛盾
    -> Arch 暂停，上报人类：发现 xxx 冲突，建议 xxx
    -> 人类确认方向后继续

触发 3：Dev 多轮自修复，仍然失败，Arch 也解决不了
    -> 上报人类：xxx feature 卡住了，原因是 xxx，已经试过 xxx
    -> 人类判断是改需求还是换技术方案
```

## 三、UAT 角色：为什么要加、能力边界在哪

### Dev checkpoint vs UAT 的区别

Dev 的 feature checkpoint 包含技术验证和局部功能验证：
- 技术层面：接口能通、不报错、返回格式正确
- 功能层面：这个 feature 本身的业务逻辑正确（发消息能存、查消息能查到）

但 Dev checkpoint 始终是**局部的**——它验证的是单个 feature 自身的正确性。

问题出在拼接处。举个例子：
- F001 消息发送 — checkpoint 通过：发消息存库成功，返回 msg_id
- F002 消息列表 — checkpoint 通过：查消息返回正确列表
- F003 流式回复 — checkpoint 通过：SSE 推送数据正确

三个各自都对，但拼在一起：发完消息后列表没有自动刷新、
流式回复结束后消息没有落库到历史、翻页时新消息和旧消息重复。

这些是**跨 feature 的场景问题**，局部 checkpoint 覆盖不到。

### 为什么加 UAT

UAT 的核心是**视角隔离**：
- 只读 app spec + module spec，不看 Arch 的 feature 拆分，不看 Dev 的实现
- 用另一个 AI 的独立理解，从产品整体出发设计验证场景
- 本质是**集成层面的交叉检验**，重点关注
  - spec 描述的用户场景是否端到端可用
  - 跨 feature 的数据流是否通顺
  - 用户场景边界情况（空数据、异常、并发）

UAT 读 app spec 是因为：module 不是孤立的，它在产品里有上下文。
比如聊天模块的"用户 session"和用户模块的"登录状态"是关联的，
只看 module spec 可能漏掉跨模块的一致性问题。

**UAT 不替代人类验收，它把人类验收的门槛降低了。** 人类拿到是 "UAT 已经从用户场景角度验过一轮、附带报告，你重点看 UAT 没法覆盖的部分"。

### UAT 的验证集要求

```
每条验证场景必须包含：

1. 场景描述：用户做什么、期望看到什么
2. 前置条件：需要什么数据/状态（→ 依赖测试数据，见 TODO）
3. 执行步骤：具体操作序列
4. 预期结果：可观测的判断标准
5. 验证方式：curl / puppeteer / 截图

示例：
{
  "scenario": "用户发送消息后，消息列表自动更新",
  "precondition": "用户已登录，聊天页面已打开，历史消息已加载",
  "steps": [
    "在输入框输入'你好'",
    "点击发送按钮",
    "等待 3 秒"
  ],
  "expected": "消息列表底部出现刚发送的消息和 AI 回复",
  "how": "puppeteer"
}
```

## 四、Feature 级 checkpoint 要求（Arch 职责）

虽然 feature checkpoint 是 AI 出题 AI 答题，但详细程度直接影响产出质量。
Arch 在拆 feature 时，checkpoint 必须做到：

**1. 写清楚完整的输入输出**

```
❌ 粗：POST /api/message 返回成功
✅ 细：POST /api/message {"content": "你好", "session_id": "abc123"}
     返回 200，body 包含 {"id": "msg_xxx", "status": "sent"}
     再 GET /api/messages?session_id=abc123 能查到这条消息
```

**2. 包含至少一个异常场景**

```
- 正常：发送消息返回 200
- 异常：session_id 不存在时返回 404，body 包含错误描述
- 异常：content 为空时返回 400
```

**3. 涉及状态变更的必须验证副作用**

```
- 发送消息后，GET 消息列表能查到
- 删除会话后，GET 该会话的消息返回 404
- 不只验"这个接口返回对了"，还要验"它对系统状态的影响对了"
```

这不能保证"做对了"，但能大幅降低"做崩了还不知道"的概率。

## 五、验收标准的真实困境

### 问题

人类能给到的最细粒度是 module spec。
到了 feature 级别的细节，人类在初始阶段想不到，也不应该要求人类想到。

### 这意味着什么

Feature 级 checkpoint = AI 局部验证 → 保证单个 feature 技术和功能正确
UAT 验证集 = 另一个 AI 从 app spec + module spec 出发交叉检验 → 拦住跨 feature 的场景问题
人类验收 = 唯一能判断"做的是不是我想要的"的环节

三层验证的关系：

```
Feature checkpoint  → 局部正确性（单个 feature 技术+功能都对）
       ↓
UAT 验证集         → 整体功能完整性（module 场景端到端通顺）
       ↓
人类验收            → 产品正确性（是不是我想要的）
```

每一层拦截不同类型的问题，但没有任何一层能替代其它层。

### 降低代价的方法

1. module 拆小（5-8 个 feature），缩短"偏了 → 发现"的周期
2. feature checkpoint 写详细，减少"做崩了不知道"的情况
3. UAT 在人类验收前先过一遍，让人类聚焦在 AI 无法判断的部分
4. 前端 UI 不预设样式标准，接受"看了再改"的迭代模式

## 六、概念层级

```
App（产品）
  └── Module（模块）
        └── Feature（具体功能）
```

| 层级 | 谁定义 | 谁验收 | 例子 |
|------|--------|--------|------|
| App | 人类 | 人类 | "做一个 AI 聊天助手" |
| Module | 人类 + Arch | UAT 整体功能验证 + 人类最终验收 | "聊天模块"、"用户模块" |
| Feature | Arch | Dev 自测（技术+局部功能）+ CI 回归 | "F001 消息发送"、"F002 流式返回" |

## 七、角色定义

### 人类
- 初始阶段（重投入）：给产品想法，和 Arch 讨论补全 app spec 和 module spec
- 运转阶段（轻投入）：收到 Arch 上报时确认/纠偏，UAT 通过后做最终验收，前端 UI 过眼
- **不参与 feature 拆解和日常开发**

### Arch
- 读 app spec + module spec + 项目规范 + 长期规范 + 历史决策
- 把 module 拆成 feature list，checkpoint 要详细（见第四节要求）
- 分配 feature 给 Dev，附带完整上下文
- 校验 Dev 完成情况
- module 所有 feature 完成后，触发 UAT 验证
- 在三种情况下上报人类
- 沉淀重要决策到 spec

### Dev
- 读 app spec + module spec + 当前 feature + checkpoint
- 按 coding.md 流程实现 + 自测
- 回报结果和阻塞
- 不做架构决策，拿不准就问 Arch

### UAT
- 只在 module 所有 feature 完成后登场
- 只读 app spec + module spec，不看 feature 拆分和 Dev 实现（视角隔离）
- 从产品整体和模块定义出发，独立设计完整验证集
- 执行验证，生成报告
- 通过 → 提交人类验收；失败 → 交给 Arch 处理

### CI/CD
- 基础设施，不是 agent
- 每次提交跑全量回归
- 结果反映在看板上

## 八、Arch 上报机制

3 种触发条件：

| 触发条件 | 上报内容 | 人类要做什么 |
|----------|----------|-------------|
| module 通过 UAT 验证 | UAT 报告 + 体验地址/截图 | 最终验收，重点看 UI 和产品感受 |
| 需求前后发现冲突 | 哪里冲突、影响范围、建议方案 | 确认方向 |
| Dev 超 2 轮自修复失败，Arch 也搞不定 | 什么 feature、卡在哪、试过什么 | 判断是改需求还是换方案 |

## 九、规范分层

| 层级 | 内容 | 例子 | 谁维护 | 变动频率 |
|------|------|------|--------|----------|
| 产品设计 | 做什么、为什么、用户场景 | "支持流式聊天" | 人类 | 跟需求走 |
| 项目规范 | 技术栈、架构约束、接口契约 | "后端 FastAPI" | Arch | 基本稳定 |
| 长期规范 | 跨项目复用的方法论 | "checkpoint 必须可执行" | 人类 | 几乎不变 |

Dev 每次开 session 注入：产品设计 + 项目规范 + 长期规范 + 当前 feature。
UAT 每次开 session 注入：产品设计 + 项目规范 + app spec + module spec。

## 十一、为什么在编程场景里这样设计

### Boris 的做法：人是调度器

Boris 同时开 5-15 个 Claude Code session，每个独立，互不通信。
他自己在窗口间切换，人脑做协调。

优点：简单、可靠、产出高（一天 22-27 个 PR）
问题：对人要求极高、不可复制、人离开就停

**Boris 证明了：人类做调度器可行，但只有极少数人能做好。**

### Slock.ai 的做法：Agent 群聊

Slock 本质是 Slack 克隆，agent 在频道里实时讨论，人类可以随时插话。

优点：直觉自然、人类随时介入、偶有灵光一闪
问题：车轱辘话多、人忍不住插话变回瓶颈、讨论无结构约束易跑偏

**Slock 证明了：agent 间实时通信有价值，但自由聊天在编程场景噪音太大。**

### 编程场景的三个特殊性

**1. 结果可验证，但验证标准难以预先完整定义**

编程的好处是代码能跑、接口能测、CI 能卡。
坏处是"做对了没"在 feature 级别人类说不清。
所以需要三层验证：Dev checkpoint（局部正确）→ UAT 验证集（整体场景通顺）→ 人类验收（是我要的）。

**2. 偏了恢复成本极高**

AI 10 分钟写 500 行，偏了恢复要半天。
所以 module 要小、断点要早、上报要及时。

**3. 信息必须分层**

产品目标、架构约束、实现细节混在一起就乱。
agent 协作必须基于结构化 feature 流转，不是自由讨论。

### 这个产品做的事

- 把 Boris 的调度能力产品化，人不用自己当调度器
- 把 Slock 的灵活度收窄成结构化流程
- 加入 UAT 层，在人类验收前先做一轮整体功能验证
- 人类只在两个时刻深度参与：开头定方向 + module 交付时验收

### 测试数据与 CI/CD 稳定性

CI/CD 要稳定执行，必须有匹配的测试数据。这个数据需要提前准备且 mock。

问题：

这不是"以后再想"的事。没有稳定的测试数据，
feature checkpoint 和 UAT 验证集都是空中楼阁。

## 十二、针对 coding 场景做新产品的独立建议

### 1. 产品核心不要做成"Agent 群聊"，而要做成"可验证的开发流水线"

如果只是把 Architect、Dev、UAT 放进一个类似 Slack 的频道里聊天，产品会很容易变成 Slock 的一个垂直皮肤：看起来热闹，但真正决定产出质量的东西没有被产品化。

coding 场景里最稀缺的不是"让 agent 说话"，而是：

- 每个 agent 当前到底在做什么
- 它依据的是哪份 spec
- 它完成的标准是什么
- 它怎么证明自己完成了
- 如果失败，失败是需求问题、实现问题、测试数据问题，还是环境问题

所以产品主线应该是：

> 把 AI coding 从"聊天驱动"变成"spec + task state + verification 驱动"。

频道、评论、线程可以有，但它们应该是辅助解释层，不应该是主工作台。

### 2. 第一版 MVP 要收窄：先做单项目、单 repo、单 Arch + 单 Dev + 单 UAT

不要一开始做多项目、多团队、多 agent 市场、多模型调度。这些看起来像平台能力，但会把最关键的问题淹没掉。

第一版只需要跑通一个很硬的闭环：

```
人类输入产品想法
  -> Arch 追问并生成 app_spec / module_spec
  -> Arch 拆 feature + checkpoint
  -> Dev 实现 + 自测
  -> CI / 本地验证
  -> UAT 从用户场景重新验收
  -> 人类看报告和体验地址
  -> 通过或打回
```

这个闭环只要真的稳定，就已经很有价值。

可以先不做复杂权限、组织、插件市场。先证明一件事：用户给一个中等复杂度功能，这套系统能比手动开多个 Claude Code session 更少操心、更少跑偏。

### 3. 最重要的产品对象不是 Agent，而是四类文件和它们的状态

建议把产品里的核心实体设计成：

| 实体 | 作用 |
|------|------|
| Spec | 说明要做什么、为什么、有哪些用户场景 |
| Feature | 从 spec 拆出来的可执行任务 |
| Checkpoint | Feature 的可验证完成标准 |
| Evidence | Dev / UAT / CI 产生的证明材料 |

Agent 只是这些实体的操作者。

这样设计有两个好处：

1. 用户不会被一堆 agent 对话淹没，而是看状态和证据。
2. 产品可以积累真正有价值的数据：什么样的 spec 容易跑偏，什么 checkpoint 有效，哪些 UAT 场景经常漏。

长期看，这些数据比"agent 会聊天"更有壁垒。

### 4. 看板不要只展示进度，要展示"可信度"

普通任务看板只告诉用户 done / doing / blocked。AI coding 产品更应该告诉用户：这个 done 到底有多可信。

建议每个 feature / module 展示：

- Spec 是否明确：是否有未解决问题
- Checkpoint 覆盖度：是否覆盖正常、异常、副作用
- Dev 自测证据：命令、结果、截图、日志
- CI 状态：是否稳定通过
- UAT 覆盖度：验证了哪些用户场景
- 人类待确认点：哪些地方 AI 不能替你判断

这会让产品从"自动写代码工具"变成"自动推进但可审计的工程系统"。

### 5. UAT 是亮点，但要警惕两个假象

UAT 这层很关键，因为它能拦住跨 feature 拼接问题。不过这里有两个风险：

**风险一：UAT 也会被 spec 误导。**

如果 app_spec / module_spec 本身漏了关键场景，UAT 不一定能凭空补出来。所以 UAT 报告里应该显式分两类：

- 已按 spec 验证通过的场景
- UAT 主动推断出的额外风险场景

第二类很重要，它能帮助人类发现"我一开始没说清楚"。

**风险二：UAT 可能只是在表面点页面。**

真正有效的 UAT 不应该只看 UI 是否出现文字，还要验证数据状态和副作用。比如：

- 页面显示创建成功后，数据库里是否真的有记录
- 刷新页面后状态是否还在
- 多用户 / 多 session 是否隔离
- 失败重试后是否产生重复数据

所以 UAT Agent 需要有明确能力边界：浏览器验证、API 验证、数据库只读检查、日志检查。否则 UAT 很容易变成"截图报告生成器"。

### 6. 测试数据和环境隔离要前置成产品能力

文末 TODO 里提到测试数据，这个判断是对的，而且它不是边缘问题，而是产品能不能成立的核心问题。

建议产品第一版就内置：

- 每个 module 的 seed 数据定义
- 测试前 reset 环境
- 外部 API mock 策略
- UAT 专用测试账号
- 每次验证的环境快照

如果没有这些，Agent 会不断卡在"我这里过了、你那里不过"。用户最后还是要人工擦屁股，产品价值会被吃掉。

### 7. Arch 的关键能力不是"拆任务"，而是"控制偏差"

很多产品会把 Architect 做成高级任务拆解器，但 coding 场景里更关键的是偏差控制。

Arch 应该持续做三件事：

1. 判断当前实现是否还贴着原始产品意图
2. 判断 Dev 的 checkpoint 是否真的覆盖了风险点
3. 判断失败应该继续修，还是回到 spec 让人类确认

也就是说，Arch 不是项目经理，也不是代码审查员，而是"产品意图和实现过程之间的守门人"。

产品上可以把 Arch 的输出固定成几种结构化动作：

- `ask_human`：需求冲突或产品判断
- `return_to_dev`：实现没达到 checkpoint
- `add_checkpoint`：发现验证遗漏
- `start_uat`：module 已具备整体验收条件
- `accept_module`：UAT 通过，提交人类最终验收

这样比让 Arch 在频道里自由长篇分析更可控。

### 8. 不建议早期追求完全无人值守

这个产品的宣传不要过早说"人类不用管，AI 自动开发完整项目"。这会把用户预期拉得太高，也会逼产品做很多脆弱的自动化。

更现实也更有价值的定位是：

> 人类仍然负责产品判断，但不再负责日常调度、重复验证和上下文搬运。

这句话更可信。

它对应的用户收益也清楚：

- 少开很多 Claude Code 窗口
- 少手动复制需求和上下文
- 少追问"做到哪了"
- 少自己写验收 checklist
- 更早发现偏差

### 9. 早期目标用户应选择"会写代码的产品型开发者"

不建议一开始面向完全不懂代码的人。

原因很简单：当前 AI coding 还没有稳定到可以让非技术用户独立兜底。完全不懂代码的用户遇到环境、依赖、测试、部署问题，会很难判断哪里错了。

更适合的早期用户是：

- 独立开发者
- 小团队 tech lead
- 会写代码的产品经理
- 高频用 Claude Code / Cursor / Codex 的开发者

他们已经相信 AI coding，但痛点是：多 session 调度累、上下文容易乱、验收靠人肉、跑偏发现太晚。

这个人群更容易理解产品价值，也更能给出高质量反馈。

### 10. 和现有工具的差异化要讲清楚

这个产品容易被问："Cursor / Claude Code / Devin / GitHub Copilot Workspace 不也在做吗？"

建议差异化不要讲"我的 agent 更多"，而要讲：

- Cursor / Claude Code：强在单次 coding 能力，但项目级调度、人类验收、跨 feature UAT 还主要靠人
- Devin 类产品：强调端到端自动完成任务，但过程可控性和人类纠偏点不一定透明
- 本产品：重点是结构化自治开发，把 spec、feature、checkpoint、evidence、UAT、人类确认串成稳定流程

一句话：

> 不是替代 coding agent，而是管理 coding agent 的工程工作台。

### 11. 可以形成壁垒的地方

长期看，壁垒不在模型调用，也不在聊天 UI，而在这些积累：

- 高质量 spec 模板
- feature 拆解模式库
- checkpoint 生成和评估方法
- UAT 场景库
- 测试数据 / mock / 环境隔离方案
- 失败原因分类数据
- 不同技术栈下的验证 recipe

这些东西会越用越强，而且贴近真实工程过程，竞争对手不容易靠一个通用聊天界面复制。

### 12. 我会建议的产品落点

如果要给这个新产品一个更清晰的定义，我建议是：

> 面向 AI coding 的结构化自治开发工作台：用 spec 驱动任务拆解，用 checkpoint 驱动实现，用 UAT 和 evidence 驱动验收，让人类只在产品判断点介入。

第一版不必做得大。只要能在一个真实 repo 上稳定完成一个 module，并且让用户明显感觉"我不用当调度器了"，这个方向就值得继续。
